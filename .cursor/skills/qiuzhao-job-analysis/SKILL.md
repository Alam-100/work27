# 岗位分析与匹配（秋招专享）

## 目标

基于情报卡 JD、可靠公开信息与求职画像，形成可追溯的岗位理解与个人匹配结论。只使用有证据支持的个人事实，不补写或美化不存在的经历。

## 路径约定

| 角色 | 路径 |
| --- | --- |
| JD / 情报卡 | `秋招/02_情报库/{公司}-{岗位}.md`（或主控指定的 stem） |
| 事实库 | `秋招/00_画像/求职画像.md` |
| 可选简历 | 用户点名文件，或 `秋招/00_画像/简历/`（缺省不阻断） |
| 产出 | `秋招/08_面试准备/{公司}-{岗位}/岗位分析与经历匹配.md` |
| 临时 | `qiuzhao/tmp/` |

可用 Obsidian MCP 或直接读 vault；字段读写可参考 `qiuzhao/scripts/vault_io.py`。

## 工作流

### 1. 确定任务范围

1. 从主控命令取得公司、岗位、情报卡 stem 及输出要求。
2. 若公司/岗位/情报卡无法唯一确定，停止并确认。
3. 定位情报卡：优先用户指定 stem；否则 `02_情报库/{公司}-{岗位}.md`；再按公司+岗位模糊匹配，多卡则询问。
4. 完整读取情报卡 frontmatter（公司/岗位/城市/要求技能/已具备/待补齐/匹配分/投递链接等）与正文「岗位简介」及投递入口。

### 2. 读取本地依据

1. 完整保留 JD 职责、任职要求、业务方向与关键词。
2. 完整读取 `求职画像.md`（技能矩阵、代表项目 STAR、勿编造标记、待确认项）。
3. 可选：读取用户指定简历或 `00_画像/简历/` 下唯一匹配文件；不得用简历覆盖画像事实。
4. 情报卡「已具备/待补齐/匹配分」可作为初值，**不得**因此跳过完整匹配矩阵。
5. 建立内部证据表：结论 ← JD 原文 / 画像位置 / 网页链接。

### 3. 联网研究公司与岗位

1. 必须联网核验公司主要业务、产品/服务、岗位所属业务线及近期相关公开信息。
2. 优先官网、官方招聘页、公告、年报；必要时可靠行业媒体与招聘平台补充。
3. 搜索具体公司+具体岗位或同类岗位，不用泛化百科替代。
4. 时效信息标注检索/发布日期；关键结论尽量交叉核验。
5. 区分「来源明确的事实」与「推断」；输出保留可点击来源链接。

### 4. 拆解岗位

1. **业务目标**：岗位最终为哪类业务结果负责。
2. **核心职责**：合并语义重复项，按重要性排序。
3. **核心能力项**：可观察、可验证的能力名（如 RAG、Agent 规划、工程落地）；避免空泛标签。
4. **能力证据**：JD 措辞或业务背景依据。
5. **可能考察方式**：标注为推断。

判断优先级：JD 频率、职责位置、硬性要求、与业务结果距离、公司业务背景。

### 5. 匹配个人经历

1. 仅从求职画像及已授权简历提取经历。
2. 对每个核心能力项给出：最匹配经历与证据、可量化结果、匹配程度（强/中/弱/缺口）、面试主讲角度、待补充项。
3. 同一经历可支持多能力，须分别解释关联。
4. 不夸大参与为主导；无证据写「画像暂无证据」并列准备缺口。

### 6. 选择面试重点

按「岗位重要性 × 证据强度 × 经历差异化 × 可讲述性」选 2–4 个主卖点。每个说明：为何重要、用哪段经历、建议讲清的行动/难点/结果、需避免的薄弱点。并列出不宜作主线、仅可补充的经历。

## 输出规范

默认写入：

```text
秋招/08_面试准备/{公司}-{岗位}/岗位分析与经历匹配.md
```

同名已存在且未要求覆盖时，先询问更新或另存。目录不存在则创建。

文档结构：

1. **岗位与资料范围**：公司、岗位、情报卡路径、本地文件、研究日期。
2. **公司与业务理解**。
3. **岗位职责拆解**。
4. **核心能力模型**。
5. **个人经历匹配矩阵**。
6. **面试主线建议**（2–4 主卖点）。
7. **风险与待确认项**。
8. **信息来源**（本地清单 + 网页链接 + 检索日期）。

本阶段**不**代写完整自我介绍或整套面试回答。

## 完成前检查

- 公司与岗位唯一明确；已读完整 JD 与求职画像。
- 公司业务与岗位背景已联网核验。
- 个人经历/数字可追溯到画像；事实与推断已区分。
- 能力项与经历逐项对应；主卖点有排序与理由。
- 产出位于 `08_面试准备/{公司}-{岗位}/` 且可打开。
